🌱 Project Plant — System Overview

A distributed microservices system for ingesting, processing, and alerting on IoT sensor telemetry.

What Does It Do?

Imagine you have 100 plant sensors in a greenhouse. Each sensor reports temperature, humidity, and soil moisture every second. Project Plant:

  1. Collects all that data through a fast API (Go Ingestion Service)
  2. Buffers it through a message queue (Kafka) so nothing gets lost
  3. Processes it with rules like "alert if temperature > 40°C" (Go Processor)
  4. Stores it in two places: fast cache (Redis) + permanent history (PostgreSQL)
  5. Displays it on a real-time dashboard (Next.js frontend)

Why So Many Pieces?

Each piece solves a specific problem. A single monolithic app could do all of this, but it would:

  • Crash under load — 1,000 sensors hitting a database directly would overwhelm it
  • Lose data — if the database goes down, all incoming data is lost
  • Be slow to change — modifying alert rules shouldn't require redeploying the API
  • Scale poorly — you can't independently scale the read vs. write path
Key Takeaway
Each technology in this stack exists because it solves a specific problem better than the alternatives. This guide teaches you what each one does and why we chose it.

🚀 Data Flow Walk-through

Follow a single sensor reading from a plant all the way to the dashboard.

Step 1: The Sensor Generates a Reading

A simulated device in Python generates a JSON payload every second:

{
  "device_id": "sensor-greenhouse-014",
  "timestamp": "2026-04-09T14:30:00Z",
  "temperature": 42.3,
  "humidity": 65.1,
  "soil_moisture": 28.7
}

The temperature of 42.3°C is above the "high temperature" threshold of 40°C. This will eventually trigger an alert.

Step 2: HTTP POST to Ingestion API

The simulator sends this JSON as an HTTP POST request to the Go ingestion service:

POST /api/v1/telemetry HTTP/1.1
Host: localhost:8080
Content-Type: application/json
X-API-Key: sk-device-014-abc123

{"device_id": "sensor-greenhouse-014", "timestamp": "...", ...}

The Ingestion API does three things in order:

  1. Authenticate: Is this API key valid? Does it match device-014?
  2. Validate: Is the JSON well-formed? Are all fields present? Are values in range?
  3. Produce: Push the event to a Kafka topic and respond 202 Accepted
Why 202, not 200?
202 Accepted means "I received your data and will process it, but processing hasn't finished yet." The data is safely in Kafka but hasn't reached Postgres yet. This is honest HTTP semantics.

Step 3: Kafka Holds the Event

The event sits in the telemetry.events Kafka topic. Think of it as a durable queue:

telemetry.events topic ┌──────────┬──────────┬──────────┬──────────┬──────────┐ │ offset 0 │ offset 1 │ offset 2 │ offset 3 │ ... │ ← new events appended here │ event │ event │ event │ OUR EVT │ │ └──────────┴──────────┴──────────┴──────────┴──────────┘ ↑ Consumer reads from here

Even if the Processor is temporarily down, the event stays in Kafka until it's consumed. Zero data loss.

Step 4: Processor Consumes and Evaluates

The Go Processor service reads the event from Kafka and runs it through the Rule Engine:

// Rule: If temperature > 40, fire "high_temperature" alert
rules := []Rule{
    {Name: "high_temperature", Field: "temperature",
     Operator: ">", Threshold: 40, Severity: "warning"},
}

// Our event has temperature=42.3 → ALERT TRIGGERED!

Step 5: Write to Storage

The Processor writes to three places simultaneously:

DestinationWhat's WrittenWhy
PostgreSQLFull event recordPermanent history for charts and queries
Redis (SET)Latest reading for device-014Instant lookup for dashboard
Redis (PUBLISH)Alert: "high_temperature on device-014"Real-time push to dashboard

Step 6: Dashboard Receives the Alert

The Dashboard API is subscribed to Redis Pub/Sub. When the alert is published, it pushes it over a WebSocket to the browser:

Redis PUBLISH "alerts:sensor-greenhouse-014" ↓ Dashboard API (Go) ← subscribed to "alerts:*" ↓ WebSocket push Browser (Next.js) ← alert toast appears instantly
Sensor Kafka → Processor Dashboard
The Big Picture
Sensor → HTTP → Kafka → Rule Engine → Postgres + Redis → WebSocket → Dashboard. Every arrow is a decoupling point. Every service can fail independently without losing data.

📦 Apache Kafka

A distributed event streaming platform that acts as the nervous system of Project Plant.

Infrastructure

What is Kafka?

Kafka is a distributed log. Think of it as a really fast, really durable conveyor belt for data. Producers put messages on the belt, consumers take messages off. The belt remembers everything for a configurable period (days, weeks, forever).

Without Kafka

Sensor → Database directly

  • Database overloaded at 1000 writes/sec
  • If DB is down, data is lost forever
  • Can't add new consumers without changing the API
With Kafka

Sensor → Kafka → Database

  • Kafka handles 100K+ messages/sec easily
  • If DB is down, Kafka retains all events
  • Add new consumers (analytics, ML) with zero changes

Key Concepts

Topics

A topic is a named category of messages. In Project Plant, we have one main topic: telemetry.events. Think of it as a database table, but append-only.

Producers

Producers write messages to topics. Our Go Ingestion API is a producer — it receives HTTP requests and writes the payload to Kafka.

// Go — producing a message to Kafka
writer := kafka.NewWriter(kafka.WriterConfig{
    Brokers: []string{"localhost:9092"},
    Topic:   "telemetry.events",
})

err := writer.WriteMessages(ctx, kafka.Message{
    Key:   []byte(event.DeviceID),  // same device → same partition
    Value: eventJSON,
})

Consumers

Consumers read messages from topics. Our Go Processor is a consumer — it reads events and processes them.

// Go — consuming messages from Kafka
reader := kafka.NewReader(kafka.ReaderConfig{
    Brokers: []string{"localhost:9092"},
    Topic:   "telemetry.events",
    GroupID: "processor-group",
})

for {
    msg, err := reader.ReadMessage(ctx)
    // process msg.Value (the telemetry event JSON)
}

Partitions

A topic can be split into partitions for parallelism. Messages with the same key (e.g., device_id) always go to the same partition, guaranteeing order per device.

telemetry.events topic with 3 partitions: Partition 0: [sensor-001, sensor-001, sensor-001, ...] ← all sensor-001 events in order Partition 1: [sensor-002, sensor-002, sensor-002, ...] ← all sensor-002 events in order Partition 2: [sensor-003, sensor-003, sensor-003, ...] ← all sensor-003 events in order 3 consumer instances can each read one partition = 3x throughput

Offsets

Every message in a partition has a sequential offset (0, 1, 2, ...). Consumers track which offset they've read up to. If a consumer crashes, it restarts from the last committed offset — no data loss, no duplicates.

Consumer Groups

Multiple consumers in the same group share the work. Kafka assigns partitions to consumers in the group so each message is processed by exactly one consumer. If a consumer dies, its partitions are automatically reassigned.

KRaft Mode (No Zookeeper)

Older Kafka versions needed a separate service called Zookeeper for coordination. Since Kafka 3.3+, this is handled internally by the KRaft consensus protocol. Project Plant uses KRaft — one fewer service to manage.

Kafka in Project Plant's docker-compose.yml

kafka:
  image: confluentinc/cp-kafka:7.9.0
  environment:
    KAFKA_PROCESS_ROLES: broker,controller     # KRaft: both roles in one node
    KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
    KAFKA_LISTENERS: PLAINTEXT://0.0.0.0:9092  # external access
    KAFKA_AUTO_CREATE_TOPICS_ENABLE: "true"     # create topics on first write
  healthcheck:
    test: ["CMD", "kafka-topics", "--bootstrap-server", "localhost:9092", "--list"]
Kafka Resilience Guarantee
If PostgreSQL goes down for 10 minutes, the Processor stops writing but Kafka retains all events. When Postgres recovers, the Processor resumes from the last committed offset and processes every buffered event. Zero data loss.

Real-World Case Study: Verkada

Verkada has thousands of cameras and sensors sending data continuously. They use event streaming (like Kafka) to decouple device communication from backend processing. When a camera detects motion, it publishes an event. Multiple downstream services (video storage, analytics, alerting) consume the same event independently. This is the exact pattern Project Plant implements.

Q: Why does the Ingestion API write to Kafka instead of directly to PostgreSQL?
Kafka is faster at storing data than PostgreSQL
PostgreSQL doesn't support JSON data
Kafka buffers events so the database isn't overwhelmed, and retains them if the database is temporarily down
Kafka is required for all microservice architectures
Correct! Kafka acts as a buffer (shock absorber) between the high-throughput API and the database. It also provides durability: if Postgres is down, events are safely stored in Kafka until Postgres recovers.
Not quite. Kafka's main value here is decoupling and resilience: it buffers high-throughput writes and retains events even when downstream services are temporarily unavailable.

🗃 PostgreSQL

The permanent, reliable storage for all historical telemetry data.

Infrastructure

What is PostgreSQL?

PostgreSQL (often called "Postgres") is a relational database. It stores data in tables with rows and columns, and lets you query it with SQL. It's the gold standard for data you can't afford to lose.

Why PostgreSQL in Project Plant?

We need to answer questions like:

  • "What was the temperature of sensor-014 at 3 PM last Tuesday?"
  • "Show me all alerts from the last 24 hours sorted by severity"
  • "How many events did we ingest in the last hour?"

Redis is fast but ephemeral. Kafka is durable but not designed for complex queries. PostgreSQL gives us durable, queryable, indexed storage.

Schema Design

Project Plant uses three main tables:

-- Table 1: Every sensor reading ever received
CREATE TABLE telemetry_events (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    device_id    TEXT NOT NULL,
    temperature  DOUBLE PRECISION NOT NULL,
    humidity     DOUBLE PRECISION NOT NULL,
    soil_moisture DOUBLE PRECISION NOT NULL,
    recorded_at  TIMESTAMPTZ NOT NULL,  -- when the sensor took the reading
    ingested_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()  -- when we received it
);

-- This index makes "get all readings for device X in time range" fast
CREATE INDEX idx_telemetry_device_time
    ON telemetry_events (device_id, recorded_at DESC);

-- Table 2: Alerts triggered by the rule engine
CREATE TABLE alerts (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    device_id    TEXT NOT NULL,
    rule_name    TEXT NOT NULL,          -- e.g., "high_temperature"
    severity     TEXT NOT NULL,          -- "warning", "critical"
    reading      JSONB NOT NULL,         -- the reading that triggered it
    triggered_at TIMESTAMPTZ NOT NULL,
    resolved_at  TIMESTAMPTZ            -- NULL if still active
);

-- Table 3: Registered devices
CREATE TABLE devices (
    device_id     TEXT PRIMARY KEY,
    api_key_hash  TEXT NOT NULL,
    profile       TEXT NOT NULL DEFAULT 'default',
    registered_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    last_seen_at  TIMESTAMPTZ
);

Key Concepts

Indexes

Without an index, finding all readings for sensor-014 requires scanning every row in the table (millions of rows = slow). An index is like the index in a textbook — it lets the database jump directly to the right rows.

-- Without index: "Scan 10 million rows" → 5 seconds
-- With index:    "Look up sensor-014 in B-tree" → 5 milliseconds
SELECT * FROM telemetry_events
WHERE device_id = 'sensor-014'
AND recorded_at > NOW() - INTERVAL '1 hour'
ORDER BY recorded_at DESC;

Migrations

Database schema changes are managed through migration files — numbered SQL scripts that are applied in order. This ensures every environment (dev, test, production) has the exact same schema.

migrations/
├── 001_create_telemetry.up.sql    -- creates telemetry_events table
├── 001_create_telemetry.down.sql  -- drops it (rollback)
├── 002_create_devices.up.sql
├── 002_create_devices.down.sql
├── 003_create_alerts.up.sql
└── 003_create_alerts.down.sql

Deduplication

If the Kafka consumer crashes and restarts, it might re-read the same event. We prevent duplicate rows with:

INSERT INTO telemetry_events (device_id, temperature, ..., recorded_at)
VALUES ($1, $2, ..., $5)
ON CONFLICT (device_id, recorded_at) DO NOTHING;
-- If this exact device + timestamp already exists, skip it

Connection Pooling (pgx)

Go uses the pgx library to talk to Postgres. It maintains a pool of connections so we don't open/close a connection for every query:

pool, err := pgxpool.New(ctx, "postgres://plant:plant@localhost:5432/plantdb")
// pool manages ~10-25 connections, reusing them for queries

Project Plant's docker-compose.yml

postgres:
  image: postgres:17-alpine          # latest stable, small image
  environment:
    POSTGRES_DB: plantdb
    POSTGRES_USER: plant
    POSTGRES_PASSWORD: plant
  volumes:
    - pgdata:/var/lib/postgresql/data  # data survives container restarts
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U plant -d plantdb"]
Test vs. Development databases
The test docker-compose.test.yml uses tmpfs (RAM disk) instead of a volume, so the database is wiped after every test run. Fast and clean.
Q: What does ON CONFLICT (device_id, recorded_at) DO NOTHING prevent?
It prevents inserting events with invalid timestamps
It prevents duplicate rows when the Kafka consumer re-processes the same event after a crash
It prevents two devices from having the same ID
It speeds up SELECT queries by creating an index
Correct! This is an idempotency mechanism. If the consumer crashes and replays a message from Kafka, the same (device_id, recorded_at) pair would be inserted again. ON CONFLICT DO NOTHING silently skips the duplicate.
Not quite. This clause specifically handles the case where the same event is inserted twice (e.g., after a consumer crash/restart). It's an idempotency mechanism.

⚡ Redis

An in-memory data store used for instant lookups and real-time alert delivery.

Infrastructure

What is Redis?

Redis is an in-memory key-value store. It stores data in RAM, which makes it incredibly fast — reads take microseconds instead of the milliseconds that disk-based databases need.

Redis Plays Two Roles in Project Plant

Role 1: Hot Cache (Latest Readings)

When the dashboard loads, it needs to show the current state of all 100 devices. Querying Postgres for the latest reading of each device is slow. Instead, we keep the latest reading in Redis:

# Store the latest reading (Go Processor does this)
SET device:sensor-014:latest '{
  "temperature": 42.3,
  "humidity": 65.1,
  "soil_moisture": 28.7,
  "timestamp": "2026-04-09T14:30:00Z"
}'

# Set a TTL (Time-To-Live) of 5 minutes
EXPIRE device:sensor-014:latest 300

# Dashboard reads it — takes < 1ms
GET device:sensor-014:latest
Why TTL?
If a device goes offline, we don't want stale data to appear as "current." The 5-minute TTL means the key automatically disappears if no new reading arrives, and the dashboard can show "offline" status.

Role 2: Pub/Sub (Real-Time Alerts)

Redis Pub/Sub is a message broadcasting system. Publishers send messages to channels; all subscribers on that channel receive them instantly.

# Processor publishes an alert
PUBLISH alerts:sensor-014 '{
  "alert_id": "alert-789",
  "rule": "high_temperature",
  "severity": "warning",
  "reading": {"temperature": 42.3}
}'

# Dashboard API is subscribed to all alert channels
SUBSCRIBE alerts:*
# → receives the message instantly
# → pushes it over WebSocket to the browser
Pub/Sub Flow: Processor ──PUBLISH──▶ Redis Channel "alerts:sensor-014" │ ┌─────────┼─────────┐ ▼ ▼ ▼ Dashboard Dashboard Dashboard API #1 API #2 API #3 │ │ │ ▼ ▼ ▼ Browser Browser Browser (WS) (WS) (WS)

Redis vs. Postgres: When to Use Which

QuestionUse RedisUse Postgres
"What is sensor-014 reading right now?"GET key — <1ms
"What did sensor-014 read last Tuesday?"SQL query with index
"Show all devices and their current state"MGET all keys — <5ms
"Average temperature per device per day"SQL aggregate query
"Push an alert to the dashboard NOW"PUBLISH — instant
This is the CQRS pattern
Using Redis for fast reads and Postgres for durable writes is an example of Command Query Responsibility Segregation. We'll cover this in detail in the Architecture Patterns section.
Q: What happens to a Redis key with a 5-minute TTL if the sensor stops sending data?
The key stays forever with the last value
Redis raises an error
The key is moved to Postgres automatically
The key automatically disappears after 5 minutes, and the dashboard can show "offline"
Correct! TTL (Time-To-Live) causes Redis to automatically delete the key after the specified duration. This prevents stale data from appearing as current when a device goes offline.
Not quite. TTL means the key automatically expires and is deleted after the specified time. No new SET means no TTL reset, so the key disappears — the dashboard then knows the device is offline.

💳 Docker & Docker Compose

Containerization: packaging applications so they run the same everywhere.

Infrastructure

What is Docker?

Docker packages an application and all its dependencies into a container — a lightweight, isolated environment that runs the same on your laptop, your teammate's laptop, and in production.

Without Docker

"It works on my machine!"

  • Install Go 1.22, Python 3.11, Kafka, Postgres, Redis manually
  • Configure paths, ports, environment variables
  • Different OS? Different versions? Hours of debugging
With Docker

docker compose up

  • One command starts everything
  • Exact same versions on every machine
  • Isolated: won't conflict with other projects

Key Concepts

Images

An image is a read-only template. Think of it as a snapshot of a filesystem with an application installed. For example, postgres:17-alpine is an image with PostgreSQL 17 pre-installed on a minimal Linux (Alpine).

Containers

A container is a running instance of an image. You can run multiple containers from the same image. Each container is isolated — it has its own filesystem, network, and processes.

Dockerfile

A Dockerfile is a recipe for building a custom image. Each service in Project Plant has one:

# Dockerfile for the Go Ingestion Service
FROM golang:1.22-alpine AS builder    # Start with Go installed
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download                    # Download dependencies
COPY . .
RUN go build -o /ingestion ./cmd/server  # Compile the binary

FROM alpine:3.19                       # Fresh, minimal image
COPY --from=builder /ingestion /ingestion  # Copy just the binary
EXPOSE 8080
CMD ["/ingestion"]                     # Run it
Multi-Stage Builds
The Dockerfile above uses two stages: builder (has Go compiler, large) and the final image (just Alpine + binary, tiny). This keeps production images small (~15MB instead of ~1GB).

Docker Compose

Docker Compose defines multiple containers that work together. Project Plant's docker-compose.yml starts Kafka, Postgres, and Redis with one command:

# Start everything
docker compose up -d --wait

# What happens:
# 1. Downloads images (first time only)
# 2. Creates containers for Kafka, Postgres, Redis
# 3. Creates a shared network so they can reach each other
# 4. Waits until health checks pass (--wait flag)

# Stop everything and clean up
docker compose down -v  # -v removes volumes (data)

Health Checks

Docker health checks verify a container is actually ready, not just running. Kafka might take 30 seconds to initialize after the container starts:

healthcheck:
  test: ["CMD", "kafka-topics", "--bootstrap-server", "localhost:9092", "--list"]
  interval: 10s     # check every 10 seconds
  timeout: 10s      # give each check 10 seconds
  retries: 10       # try 10 times before marking unhealthy
  start_period: 30s # wait 30s before first check

🐶 Go (Golang)

The language powering all three backend services: Ingestion, Processor, and Dashboard API.

Language

Why Go for Backend Services?

  • Concurrency: Goroutines handle thousands of simultaneous connections with minimal memory
  • Performance: Compiled to native code — as fast as C, easier to write
  • Simplicity: Small language spec (25 keywords). Easy to learn, easy to read others' code
  • Standard library: Production-grade HTTP server built in — no framework needed
  • Fast compilation: Compile a full service in <5 seconds
  • Verkada uses Go for their backend services — directly relevant experience

Key Go Concepts Used in Project Plant

Goroutines

A goroutine is a lightweight thread managed by the Go runtime. They cost ~2KB of memory (vs ~1MB for OS threads). You can run millions of them.

// Each incoming HTTP request runs in its own goroutine automatically
// The Go HTTP server does this for you:
http.HandleFunc("/api/v1/telemetry", handler)
http.ListenAndServe(":8080", nil)
// → 1000 simultaneous requests = 1000 goroutines ≈ 2MB of memory

Interfaces

Go interfaces enable dependency injection and testability. Project Plant defines interfaces for every external dependency:

// In the Ingestion API, we define WHAT we need, not HOW it works
type EventProducer interface {
    Produce(ctx context.Context, event TelemetryEvent) error
    Close() error
}

// Real implementation: writes to Kafka
type KafkaProducer struct { writer *kafka.Writer }
func (k *KafkaProducer) Produce(ctx context.Context, event TelemetryEvent) error {
    return k.writer.WriteMessages(ctx, kafka.Message{Value: eventJSON})
}

// Test implementation: records calls in memory
type MockProducer struct { events []TelemetryEvent }
func (m *MockProducer) Produce(ctx context.Context, event TelemetryEvent) error {
    m.events = append(m.events, event)
    return nil
}

// The handler doesn't care which one it gets!
func NewHandler(producer EventProducer) http.Handler { ... }
Why Interfaces Matter
Without interfaces, unit-testing the HTTP handler would require a running Kafka broker. With interfaces, we swap in a mock and test the handler in isolation in milliseconds.

Table-Driven Tests

Go's idiomatic testing pattern. Define all test cases in a slice and loop through them:

func TestValidate(t *testing.T) {
    tests := []struct {
        name    string
        event   TelemetryEvent
        wantErr bool
    }{
        {"valid event", TelemetryEvent{DeviceID: "d1", Temperature: 25}, false},
        {"empty device ID", TelemetryEvent{DeviceID: ""}, true},
        {"temperature too high", TelemetryEvent{DeviceID: "d1", Temperature: 81}, true},
        {"temperature too low", TelemetryEvent{DeviceID: "d1", Temperature: -41}, true},
        {"boundary min temp", TelemetryEvent{DeviceID: "d1", Temperature: -40}, false},
        {"boundary max temp", TelemetryEvent{DeviceID: "d1", Temperature: 80}, false},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            err := tt.event.Validate()
            if (err != nil) != tt.wantErr {
                t.Errorf("Validate() error = %v, wantErr = %v", err, tt.wantErr)
            }
        })
    }
}

Build Tags for Test Separation

Integration tests (that need real Kafka/Postgres) are separated from unit tests with build tags:

//go:build integration

package integration_test

// This file only compiles when you run:
// go test -tags=integration ./integration_test/...
//
// Regular "go test ./..." skips it entirely

Go Modules

Each service has its own go.mod file listing dependencies. This is like package.json in Node.js or requirements.txt in Python:

module github.com/danielkuo/project-plant/services/ingestion

go 1.22

require (
    github.com/segmentio/kafka-go v0.4.47
    github.com/stretchr/testify v1.9.0
    go.uber.org/zap v1.27.0
)

Kafka doesn't work with Go, so we need a wrapper
So we can swap in a mock during tests without needing a real Kafka broker
Because Go requires all types to implement interfaces

Correct! Interfaces enable dependency injection. The HTTP handler is tested with a MockProducer (fast, no infrastructure needed). In production, a real KafkaProducer is injected. Same code, different implementations.
The main reason is testability through dependency injection. The handler depends on the EventProducer interface, so we can inject a mock for unit tests and real Kafka for integration tests.

🐍 Python & asyncio

Powers the device simulators, adapter SDK, and computer vision service.

Language

Why Python for Simulators?

  • Rapid prototyping: Faster to write simulator logic than in Go
  • asyncio: Python's async framework lets us simulate 100+ devices concurrently
  • Hardware ecosystem: Python has the best libraries for Raspberry Pi, sensors, GPIO
  • Data science integration: Easy to add ML models or data analysis later

asyncio: Doing Many Things at Once

asyncio lets a single Python process handle many I/O operations concurrently. Perfect for simulating 100 sensors that each send data every second.

import asyncio

class Device:
    def __init__(self, device_id: str):
        self.device_id = device_id
        self.temperature = 25.0  # starting temperature

    async def start(self):
        """Generate readings at ~1Hz with realistic drift."""
        while True:
            # Random walk: temperature changes by -0.5 to +0.5 each tick
            self.temperature += random.uniform(-0.5, 0.5)
            self.temperature = max(-40, min(80, self.temperature))  # clamp to range

            yield {
                "device_id": self.device_id,
                "timestamp": datetime.now(UTC).isoformat(),
                "temperature": round(self.temperature, 2),
                "humidity": round(self.humidity, 2),
                "soil_moisture": round(self.soil_moisture, 2),
            }
            await asyncio.sleep(1)  # non-blocking 1-second pause
async/await vs. threads
await asyncio.sleep(1) doesn't block the thread — it says "pause this coroutine for 1 second and let other coroutines run." This means 100 Device coroutines share one thread, each taking turns. Much lighter than 100 OS threads.

The Fleet Orchestrator

class Fleet:
    def __init__(self, count: int, profile: str = "tropical"):
        self.devices = [Device(f"sensor-{i:03d}", profile) for i in range(count)]

    async def run(self):
        """Run all devices concurrently."""
        tasks = [device.start() for device in self.devices]
        await asyncio.gather(*tasks)  # all devices run in parallel

# Start 100 simulated sensors:
# python -m simulators --count 100 --profile tropical --api-url http://localhost:8080

Abstract Base Classes (ABCs)

The Device Adapter SDK uses Python ABCs to define the interface that all sensor implementations must follow:

from abc import ABC, abstractmethod

class SensorAdapter(ABC):
    """Every sensor (simulated or real hardware) implements this."""

    @abstractmethod
    async def initialize(self) -> None:
        """Set up hardware: open GPIO, calibrate sensors."""
        ...

    @abstractmethod
    async def read(self) -> SensorReading:
        """Take a single reading. Returns temp, humidity, soil_moisture."""
        ...

    @abstractmethod
    async def cleanup(self) -> None:
        """Release hardware resources."""
        ...

# The simulated adapter (what we use now):
class SimulatedAdapter(SensorAdapter):
    async def read(self) -> SensorReading:
        return SensorReading(
            temperature=self.temp + random.uniform(-0.5, 0.5), ...
        )

# A future real hardware adapter:
class RPiDHT22Adapter(SensorAdapter):
    async def read(self) -> SensorReading:
        import adafruit_dht
        sensor = adafruit_dht.DHT22(board.D4)
        return SensorReading(temperature=sensor.temperature, ...)

Q: What does await asyncio.sleep(1) do differently than time.sleep(1)?
It pauses only the current coroutine, letting other coroutines run during the pause
It sleeps for exactly 1 millisecond instead of 1 second
It runs in a separate thread automatically

The key difference is blocking vs non-blocking. time.sleep(1) blocks the whole thread. await asyncio.sleep(1) suspends only the current coroutine, freeing the thread for other coroutines.

function useWebSocket(url: string) {

🔀 CQRS Pattern

Command Query Responsibility Segregation: separate paths for reading and writing data.

Architecture Pattern

The Problem

Writing sensor data and reading it for the dashboard have very different requirements:

Writes (Commands)Reads (Queries)
Volume500+ events/sec from 100 sensors~10 requests/sec from dashboards
Latency toleranceCan be async (202 Accepted)Must be instant (<100ms)
Data shapeSingle event insert"Give me all devices + latest readings"
OptimizationBatching, append-onlyIndexed lookups, aggregations

The Solution: Two Separate Paths

WRITE PATH (Commands) Sensor → Ingestion API → Kafka → Processor → Postgres (append) → Redis SET (update latest) READ PATH (Queries) Dashboard → Dashboard API → Redis GET (current state, <1ms) → Postgres SELECT (history, indexed)

Why Not Just Use One Database?

If the dashboard queried Postgres for "latest reading of all 100 devices" on every page load:

-- This query joins and sorts 100 devices × millions of rows:
SELECT DISTINCT ON (device_id) *
FROM telemetry_events
ORDER BY device_id, recorded_at DESC;
-- Result: ~200ms under load, competes with write queries for connections

With Redis as the read cache:

-- Pre-computed: each device's latest reading is a single key
MGET device:sensor-001:latest device:sensor-002:latest ... device:sensor-100:latest
-- Result: ~2ms, doesn't touch Postgres at all
CQRS Trade-off
Pro: Reads are blazing fast and don't compete with writes. Con: There's a brief delay (usually <1 second) between when data is written and when it appears in the read cache. This is called eventual consistency. For a sensor dashboard, this is perfectly acceptable.
Q: In CQRS, what does "eventual consistency" mean?
Data is always consistent across all stores
Data is only written to one store at a time
There's a brief delay between writing data and it appearing in the read store, but it will catch up
Data is never consistent and can be lost
Correct! When the Processor writes to Postgres and Redis, there's a small window where a dashboard read might see slightly stale data. Within milliseconds to seconds, both stores are consistent. This is the trade-off for having incredibly fast reads.
Eventual consistency means the read store (Redis) may lag slightly behind the write store (Postgres) — usually by milliseconds. But it will converge. The data is not lost; it's just briefly out of date in one location.

🔌 WebSockets & Pub/Sub

Real-time communication from server to browser without polling.

Architecture Pattern

The Problem with HTTP Polling

If the dashboard uses regular HTTP to check for new data:

// Bad: polling every second
setInterval(async () => {
  const data = await fetch('/api/v1/devices');
  updateUI(data);
}, 1000);
// 100 dashboard users × 1 request/sec = 100 req/sec of wasted requests
// Most responses: "nothing new" (304 Not Modified)

WebSockets: Persistent Two-Way Connection

A WebSocket starts as an HTTP request, then upgrades to a persistent, bidirectional connection. The server can push data to the client at any time without the client asking.

HTTP Polling: Client: "Any updates?" → Server: "No" (wasted) Client: "Any updates?" → Server: "No" (wasted) Client: "Any updates?" → Server: "Yes! Here's data" Client: "Any updates?" → Server: "No" (wasted) WebSocket: Client ←——————persistent connection——————→ Server (server pushes when ready) Server: "Here's new data!" → Client Server: "Alert! Temp too high!" → Client

How It Works in Project Plant

1. Browser opens WebSocket to Dashboard API ws://localhost:8081/api/v1/ws/events 2. Dashboard API subscribes to Redis Pub/Sub SUBSCRIBE alerts:* 3. When Processor publishes an alert: PUBLISH alerts:sensor-014 {"rule": "high_temperature", ...} 4. Redis delivers to Dashboard API instantly 5. Dashboard API pushes to ALL connected WebSocket clients 6. Browser shows alert toast — no polling needed!

The WebSocket Hub Pattern (Go)

// The Hub manages all connected WebSocket clients
type Hub struct {
    clients    map[*Client]bool
    broadcast  chan []byte
    register   chan *Client
    unregister chan *Client
}

func (h *Hub) Run() {
    for {
        select {
        case client := <-h.register:
            h.clients[client] = true  // new browser connected

        case client := <-h.unregister:
            delete(h.clients, client)  // browser disconnected

        case message := <-h.broadcast:
            // Send to ALL connected browsers
            for client := range h.clients {
                client.send <- message
            }
        }
    }
}

// When Redis Pub/Sub receives an alert:
func (s *Server) onRedisMessage(msg redis.Message) {
    s.hub.broadcast <- []byte(msg.Payload)  // fans out to all browsers
}

Redis Pub/Sub vs. Kafka

KafkaRedis Pub/Sub
PersistenceMessages stored on disk for daysFire-and-forget (no history)
DeliveryAt-least-once (can replay)At-most-once (miss it, it's gone)
Use caseDurable event pipelineReal-time notifications
In Project PlantSensor data pipelineAlert push to dashboards
Why not use Kafka for WebSocket push?
Kafka is designed for durable, replayable event logs — it's overkill for ephemeral UI notifications. Redis Pub/Sub is instant and lightweight. If a browser isn't connected when an alert fires, they'll see it in the alerts list (from Postgres) when they reconnect.

🔌 Adapter Pattern

Making the system work with any sensor hardware without changing backend code.

Design Pattern

The Problem

Today we use simulated sensors. Tomorrow we might use a Raspberry Pi with a DHT22 sensor. Next month, an ESP32 with a soil moisture probe. Each has different hardware APIs, but the backend shouldn't need to change for each one.

The Solution: SensorAdapter ABC

Define a common interface. Every sensor implements three methods. The SDK handles everything else.

What you implement (one class per hardware type): ┌────────────────────────────────────────┐ │ class YourAdapter(SensorAdapter): │ │ async def initialize(self): ... │ ← set up GPIO, calibrate │ async def read(self): ... │ ← return one reading │ async def cleanup(self): ... │ ← release hardware └────────────────────┬───────────────────┘ │ What the SDK handles (you don't touch this): ┌────────────────────┴───────────────────┐ │ Device SDK │ │ ├── 1Hz reading loop │ │ ├── JSON serialization │ │ ├── HTTP transport + retries │ │ ├── API key authentication │ │ ├── Error recovery + reconnection │ │ └── Graceful shutdown │ └─────────────────────────────────────────┘

Three Adapter Implementations

# 1. Simulated (what we use now)
class SimulatedAdapter(SensorAdapter):
    async def read(self) -> SensorReading:
        self.temp += random.uniform(-0.5, 0.5)  # random walk
        return SensorReading(temperature=self.temp, humidity=..., soil=...)

# 2. Raspberry Pi with DHT22 sensor (future)
class RPiDHT22Adapter(SensorAdapter):
    async def read(self) -> SensorReading:
        sensor = adafruit_dht.DHT22(board.D4)
        return SensorReading(temperature=sensor.temperature,
                             humidity=sensor.humidity, soil=self.read_adc())

# 3. ESP32 via Serial (future)
class ESP32SerialAdapter(SensorAdapter):
    async def read(self) -> SensorReading:
        self.serial.write(b"READ\n")
        line = await self.serial.readline()
        data = json.loads(line)
        return SensorReading(**data)
Zero Backend Changes
When you add a new hardware adapter, you change nothing in the Go ingestion service, the Kafka pipeline, the processor, or the database. The adapter produces the same JSON payload; the rest of the system doesn't know or care whether it came from a simulation or a real sensor.

Real-World Analogy

Think of a USB port. Your computer doesn't care if you plug in a keyboard, mouse, or webcam. The USB standard defines the interface; each device implements it differently. The SensorAdapter is our "USB standard" for plant sensors.

📜 JSON Schema & Contracts

A single source of truth that keeps Go, Python, and TypeScript in sync.

Architecture Pattern

The Problem

When multiple services in different languages exchange data, they need to agree on the format. Without a contract:

  • Python simulator sends temp, but Go expects temperature — runtime error
  • Go allows temperature up to 100, Python validates up to 80 — inconsistent rules
  • Frontend expects soil_moisture as a number, backend sends a string — chart breaks

The Solution: One JSON Schema File

// schemas/telemetry_event.json — THE source of truth
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "TelemetryEvent",
  "type": "object",
  "properties": {
    "device_id":     { "type": "string", "minLength": 1 },
    "timestamp":     { "type": "string", "format": "date-time" },
    "temperature":   { "type": "number", "minimum": -40, "maximum": 80 },
    "humidity":      { "type": "number", "minimum": 0, "maximum": 100 },
    "soil_moisture": { "type": "number", "minimum": 0, "maximum": 100 }
  },
  "required": ["device_id", "timestamp", "temperature", "humidity", "soil_moisture"],
  "additionalProperties": false
}

Contract Tests: Cross-Language Validation

Both Go and Python tests validate against the same schema file:

        "device_id": "sensor-001",

    }

        DeviceID: "sensor-001",

    // validate data against same
    // schemas/telemetry_event.json

Why This Matters
If someone changes the schema (e.g., adds a new field), contract tests in both languages will catch any mismatch during CI. No more "it works in Python but breaks in Go" surprises.
Q: What does "additionalProperties": false do in the JSON Schema?
It makes all properties optional
It prevents nested objects
It allows any extra fields to be added
It rejects payloads that contain fields not defined in the schema
Correct! With this set to false, a payload like {"device_id": "x", ..., "color": "green"} would be rejected because "color" is not in the schema. This enforces a strict contract — no surprise fields sneaking through.
This setting rejects any JSON object that contains fields not explicitly listed in the schema's "properties." It enforces strict contracts by preventing unknown fields from passing validation.

📈 Load Testing (k6 + vegeta)

Proving the system handles 500+ events/sec without breaking.

Testing

Why Load Test?

Your system works with 1 request. Does it work with 500/sec for 30 minutes? Load testing reveals:

  • Memory leaks (usage grows over time)
  • Connection pool exhaustion (database/Kafka connections run out)
  • Latency degradation (p99 increases under sustained load)
  • Queue backpressure (Kafka consumer can't keep up)

  });
